One system for everyone who shares a workshop.

TinkerCommons is a planned open-source system for makerspaces, hackerspaces, community media centers, public-access TV stations and tool libraries. Members, dues, waivers, badges, bookings, door and tool access, and one ledger that reconciles to Stripe, in place of the several tools a space usually stitches together.

Read the spec View on GitHub
Nothing to install yet. This repository holds research and a written specification. There is no runnable code, no release and no demo. Everything below describes what the spec says the system will do.

Why it exists

The project's research (25 commercial tools and 25 open-source repositories, per its synthesis) concludes that no product covers the shared core, and that open-source options are mostly one-space systems.

Coworking platforms

Handle doors and bookings, but per the research have no certifications, no metered billing and no classes.

Makerspace tools

Handle certifications and machine lockout, but are closed and priced from $64 to $960 a month; only one ships door access.

Open source today

Twenty-plus repositories, nearly all written by one hackerspace for itself, several with no licence file.

Read the full research synthesis.

Access follows state

The central design rule. A fob, phone or PIN works only while the member passes every check. The door or machine controller does not keep its own list of who is allowed, beyond a short offline cache.

  1. Activemembership is in good standing
  2. Paid updues not overdue past the grace period
  3. Waiveredwaiver signed
  4. Badgedholds the badge the device requires

Pass all four and the door opens or the machine powers on. Miss one and it stays shut. The access protocol controls door release and power enable only; emergency stops and machine safety interlocks are never routed through it.

planned: v0.5 The protocol is to be published openly, with adapters for UniFi Access first, then Kisi, then one of Verkada or Genea, plus reference ESP32 firmware for tool interlocks. TinkerCommons keeps its own access events rather than ingesting a provider's logs.

What the spec covers

Every item is specified. None is built.

Members and dues

One record per person, membership classes, recurring dues through Stripe Billing, roles scoped per shop.

Waivers and badges

Versioned documents signed in-app with a stored PDF; certifications with expiry and grant evidence.

Resources and bookings

Studios, shops and machines booked from a phone under a per-resource, per-tier rule table, including included hours.

One ledger

Dues, bookings, metered tool use, consumables, classes, donations and cash in one ledger that reconciles to Stripe.

Door and tool access

Fobs, cards, PINs and phone keys tied to member state, with tool sessions billed by the minute.

Reports and export

Who is active or overdue, utilization, revenue by shop. Full CSV and JSON export of every table from the first version.

Principles

Eight rules from the spec. The design is not to violate them without changing the spec.

01

One of each

One record per member, one ledger per space, one login.

02

Rules are data

Pricing, included hours, booking windows and badge requirements are table rows, not code paths.

03

Access follows state

Paid up, waivered, badged, or the door stays shut.

04

No card numbers

Stripe holds payment methods; the system stores Stripe IDs.

05

Export from day one

Not the lock-in it sets out to replace.

06

Self-host first

One Docker command to install. Hosted is optional, never required.

07

Hardware is a plug-in

A published protocol and adapters. No hardware is sold.

08

Proof before done

Every version ships with acceptance tests passing on real data at a reference site.

Version ladder

Versions are sequential. All of these are planned; none has shipped. Source: section 9 of the master spec. No dates are committed.

  1. v0.1Foundation first targetMembers, membership classes, Stripe dues, roles, audit log, full export, Docker install.
  2. v0.2Documents and badgesVersioned waivers with in-app signing, badges with expiry and grant evidence.
  3. v0.3Resources and bookingsBooking-rule table, phone calendar, recurring bookings, approvals, included hours.
  4. v0.4Ledger and paymentsCharge types, invoices, offline payments, taxes, credits, Stripe meters and Terminal.
  5. v0.5AccessPublished protocol, ESP32 firmware, UniFi and Kisi adapters, tool sessions billed by the minute.
  6. v0.6Classes and eventsSessions, capacity, member pricing, attendance, classes that grant badges.
  7. v0.7Reports and importersStaff reports, email notices, Wild Apricot and CSV importers, public JSON API and webhooks.
  8. v0.8HardeningPrivacy controls, tested restore, one-command upgrade, 2FA for staff, security review.
  9. v0.9PilotRun alongside current tools at two reference sites for a full billing cycle.
  10. v1.0ReleaseEverything above, with documentation, installer and migration guide.
  11. v2.0Full briefEquipment rental, governance, shop-captain UI, CivicCast intake, multi-location, gift cards.
  12. v3.0Beyond the briefOptional; to be decided after v2.0.

Non-goals in every version: hosting chat or forums, selling hardware, a website builder, an accounting ledger beyond what reconciles to Stripe and exports to QuickBooks, replacing CivicCast's broadcast functions.

Status

Done

  • Research: Proximity teardown, commercial and open-source landscapes, doors, payments, migration and hosting.
  • Decisions: name, licence, stack, pilot order, door providers.
  • Master spec (version 0.2.0), a v0.1 plan and an implementation plan.

Not done

  • No code, no tests, no CI, no releases, no installer.
  • No hosted service or demo.
  • Next step in the project's state file: unit U1, a Django skeleton with Compose and a health endpoint.

Reference sites named in the spec: TinkerMill and Longmont Public Media, both 501(c)(3) nonprofits in Longmont, Colorado. The spec says no records from either site are used; fixtures are to be synthetic.
